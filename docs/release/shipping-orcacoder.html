OrcaCoder V3 · Release guide · 26 August 2026

Shipping OrcaCoder

Twelve steps take a change in the code and turn it into an update running on someone's machine. This is what each one does, and who has to start it.

Eight of the twelve steps need a person. None of them starts because the step before it finished. Once the line on the left turns blue, the process waits for you.

The twelve steps

Read top to bottom. The colour of each step tells you who acts.

Claude does it Happens on its own You start it by hand Stop and look

Part one · Getting the code in

1

Change the code

Claude

Write it, run the tests, commit it. Nothing gets pushed that has not been run.

2

Push it to a branch

Claude

It goes to a branch on OrcaCoder V3, never straight to the main line. GitHub refuses that anyway.

Runs: git push origin HEAD:test/updater-pipeline
3

Open a pull request

Claude

A pull request asks to add the work to orca-main, the main line. Asking is all it does. Nothing is added yet.

4

The checks run

Automatic

Nobody starts this. Opening the pull request starts it. Types are checked, tests run, and the whole app is built on Windows and on macOS.

The Windows app build takes about twelve minutes when the cache is warm, and considerably longer when it is not.

Watch it: the Actions tab, workflow named CI
5

You merge it

You

Only when every check is green. A red check means it does not go in. This is where the work joins the main line, and where the process starts waiting for you.

Part two · Proving it works

6

You rehearse the update

You

This builds an installer, signs it with a throwaway key, and puts together a test release that no real person can reach. It answers the question that matters most: does updating an existing copy break anything?

A fresh install working proves very little. Most update problems only appear when installing over a version that is already there.

Start: Actions → Desktop isolated update test → Run workflow

Part three · Building and signing

7

You build the candidate

You

This is the real installer. You type in the exact commit and the exact version, such as 0.54.0. Typing them by hand is the safeguard: it is hard to release the wrong thing by accident.

Start: Actions → Desktop candidate → Run workflow
8

You sign it

You

Signing is what stops Windows warning the person who installs it. An unsigned installer still works, but it shows a blue warning box that has to be clicked past.

You give it the ID of the run from step 7, so it signs that exact build and no other.

Start: Actions → Desktop protected signing → Run workflow

Part four · Checking and releasing

9

You stage a draft

You

A draft release is assembled but hidden. Nobody can download it. This exists so there is something finished to look at before it goes out.

Start: Actions → Desktop publication → operation: stage-draft
10

You look at the draft

Stop and look

The last point where stopping costs nothing. Is it the right version number? Are the notes right? Is the file the one you meant to build?

Publication is deliberately split into two separate runs so this gap exists. It is not a formality — it is the only place a wrong build gets caught before other people have it.

11

You publish it

You

This is the moment it is out. Everything before this can be thrown away quietly.

Start: Actions → Desktop publication → operation: publish-reviewed-draft
12

You put it on the machine

You

Copy the installer across and run it. The app does not check for updates and will not update itself. That is switched off on purpose until there is a place to host the files and a key to prove a download is genuine.

Two things will stop you right now

Both are known. Neither is a mystery. The first one blocks every pull request until somebody changes a setting.

No pull request can merge yet

The main line is protected, and the protection asks for six checks before anything may merge. Only four of them exist. The two missing ones are for Ubuntu, and a required check that never starts waits forever.

The fix is to change the setting so it asks for the four checks that actually run. That needs someone with admin rights on the repository. The alternative is to add Ubuntu to the checks, which is only worth doing if anyone is genuinely going to run OrcaCoder on Linux.

A Mac build cannot be given to anyone yet

macOS is built on every pull request and kept for seven days, so you can download it and try it. It is not signed, which is fine for testing on a Mac you control and not fine for anyone else.

Handing a Mac build to a person needs an Apple Developer account. Without one, current macOS can report the app as damaged and refuse to open it, which is worse than the Windows warning. Testing it properly also needs a real Mac, though renting one by the hour is enough — there is no need to buy one.

Testing a Mac build without owning a Mac

This one catches people, because the obvious order does not work.

A Mac app cannot be built on Windows

It needs Apple's own tools, and those only run on Apple computers. There is no way around it, and nothing to copy across. The building has to happen on a Mac before any testing can start.

You do not have to buy one. You rent two things briefly: a Mac that builds, and a Mac you can look at.

The loop

1

GitHub builds it

Automatic

GitHub rents Apple computers by the minute and keeps Apple's tools installed on them. Every pull request builds the Mac version on one, and keeps the result for seven days.

You do nothing. It happens because the pull request opened.

Find it: Actions → the CI run → Artifacts → orcacoder-macos-unsigned
2

You rent a Mac for an hour

You

A cloud Mac is a real Apple computer in a data centre that you connect to like a remote screen. Rent it when you need it, hand it back after, and pay for the time you used.

Services such as MacinCloud or Scaleway suit this. Avoid Amazon's Mac service for short checks — it charges a minimum of twenty-four hours per machine.

3

Download it on that Mac

You

The rented Mac has its own web browser. Sign in to GitHub there and download the build straight onto it.

Do not download it on your PC and send it over. That is a longer trip for the same file, and passing a Mac app between machines can damage it.

4

Right-click, then Open

Expect this

The build is not signed, so macOS refuses a plain double-click. Right-click the app and choose Open instead. That offers a way through; a double-click does not.

This is expected, and it is not a fault in the app. It only becomes a real problem when handing the app to somebody else, which is what signing solves.

5

Test it, then give the Mac back

You

GitHub's build proves the code compiles. It cannot tell you whether the window looks right or the app behaves. That is the reason to rent a screen you can sit in front of.

Stop the rental when you are finished.

Before anyone else can open a Mac build, it has to be signed and sent to Apple to be checked. That needs an Apple Developer account, which costs a yearly fee. Until then, Mac builds are for testing only.

When something goes wrong

Four failures that have actually happened here, and what they mean.

What you seeWhat it means
A check is red Something broke. Open the check, read the failing step. Do not merge around it.
A check sits on "Expected" and never starts The protection is asking for a check that does not exist. See the first blocker above.
The build says it succeeded but no file appeared It did not run. Check the time on the file, not the success message. This has happened here.
Your change is missing from the installer The sidecar was not rebundled. That step is not automatic, and skipping it still reports success.

Words you will see

Plain meanings for the terms that come up in the Actions tab and in this guide.

Repository
A project's code on GitHub, with its full history. OrcaCoder V3 has one; the board was taken from a different one.
Branch
A separate line of work. You change a branch freely without touching the main line.
Main line
Here it is called orca-main. The version of the code that counts. It is protected, so nothing goes in without passing the checks.
Pull request
A request to add a branch's work to the main line. It runs the checks and shows exactly what would change.
Checks
Automatic tests and builds that run on a pull request. Green means safe to merge. Red means stop.
Commit
One saved change, with a note saying what it was and why. Every release names an exact commit.
Sidecar
The background program that does the real work behind the app window. It is built separately, then bundled in.
Signing
Marking the installer with a private key so Windows can confirm who made it, and stop warning the person installing it.
Notarizing
Apple's version of the same idea. The build is sent to Apple, checked, and given a ticket. Needed before a Mac build can be handed to anyone.
Draft release
A finished release that is still hidden. It exists so somebody can look at it before it goes out.

The written version, with more detail, is at docs/release/github-and-updates.md.
